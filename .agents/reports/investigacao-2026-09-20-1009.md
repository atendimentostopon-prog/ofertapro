# Investigação — erro ao revelar API Key

Data: 20/09/2026 10:09 (America/Sao_Paulo)

## 1. Resumo

Ao clicar no ícone de olho, o frontend invoca a Edge Function `api-key-reveal`. A mensagem exibida — `Edge Function returned a non-2xx status code` — não é a causa original; é o erro genérico do SDK Supabase quando o endpoint responde com 4xx/5xx.

A causa mais provável é que `api-key-reveal` não foi implantada (ou está com uma versão/configuração divergente) no projeto Supabase usado pela aplicação. A função existe no repositório desde 28/08/2026, porém o procedimento de deploy continua listando apenas `api-key-generate`, `api-key-revoke` e `public-api`. Falta o status HTTP e o log remoto da invocação para confirmar definitivamente.

## 2. Causa raiz e confiança

### Causa mais provável — divergência de deploy da Edge Function (confiança: Média)

**FATOS**

- O botão do olho chama `handleToggleReveal` em `src/components/settings/ApiIntegrationsTab.tsx:144-165`.
- Esse handler chama `ApiKeyService.revealApiKey()` em `src/components/settings/ApiIntegrationsTab.tsx:154`.
- O serviço invoca explicitamente `api-key-reveal` por POST em `src/services/ApiKeyService.ts:53-62`.
- Qualquer erro retornado pelo SDK é relançado sem extrair o corpo da resposta (`src/services/ApiKeyService.ts:58-60`), por isso o toast mostra somente a mensagem genérica vista na imagem.
- A implementação local da função está em `supabase/functions/api-key-reveal/index.ts` e foi criada no commit `91dc0c0` de 28/08/2026; sua integração com Vault mudou no commit `f1118a4` de 31/08/2026.
- O guia `API_E_INTEGRACOES_LINK_OFERTA.md:148-154` manda implantar `api-key-generate`, `api-key-revoke` e `public-api`, mas omite `api-key-reveal`.
- Não há teste automatizado de `api-key-reveal`; as únicas referências encontradas são o componente e o serviço.
- A chave ativa mostrada na imagem foi criada em 06/09/2026, depois da criação local da função, mas isso não comprova que a função tenha sido implantada.

**HIPÓTESE MAIS PROVÁVEL**

O frontend foi publicado contendo o botão e a chamada, mas a função `api-key-reveal` não foi implantada junto (ou o deploy remoto ainda contém uma versão incompatível). Nesse caso o gateway retorna um status não-2xx, e o SDK o converte exatamente na mensagem exibida.

**O que falta para confirmação**

- No DevTools > Network, capturar o status e o corpo de `POST /functions/v1/api-key-reveal`.
- No Dashboard Supabase > Edge Functions, confirmar se `api-key-reveal` existe, versão/data do último deploy e consultar o log no horário do clique.
- Resultado esperado: 404/`Function not found` confirma função ausente; 401 confirma autenticação/JWT; 500 com log confirma falha interna/configuração.

## 3. Fluxo até o erro

1. Usuário autenticado abre a tela de integrações; a lista de chaves é lida diretamente de `api_keys` sob RLS (`src/services/ApiKeyService.ts:20-30`).
2. O componente encontra a chave com `status === 'active'` e mostra o olho (`src/components/settings/ApiIntegrationsTab.tsx:178`, `282-297`).
3. O clique executa `handleToggleReveal` e ativa o estado de carregamento (`src/components/settings/ApiIntegrationsTab.tsx:144-165`).
4. O serviço chama `supabase.functions.invoke('api-key-reveal', { method: 'POST' })` (`src/services/ApiKeyService.ts:53-56`).
5. Em caso de sucesso, a função valida o JWT, procura a chave ativa, lê o segredo do Vault via RPC, confere seu SHA-256 e retorna a chave (`supabase/functions/api-key-reveal/index.ts:29-96`).
6. Nesta ocorrência, a chamada recebeu resposta não-2xx antes de chegar a uma resposta de sucesso. O serviço relançou o erro do SDK (`src/services/ApiKeyService.ts:58-60`) e o componente exibiu `err.message` (`src/components/settings/ApiIntegrationsTab.tsx:161-164`).

## 4. Hipóteses, evidências e descarte

### H1 — função ausente/desatualizada no Supabase remoto (mais provável)

- A favor: função adicionada depois do trio original; documentação de deploy a omite; Edge Functions exigem deploy explícito e commit no Git/Vercel não as publica.
- Contra: não foi consultado o inventário remoto, portanto ela pode existir.
- Como confirmar: status 404 no Network ou ausência no Dashboard; comparar data/versão implantada.

### H2 — JWT ausente, inválido ou expirado

- A favor: a função retorna 401 se o header não existir ou `auth.getUser()` rejeitar o token (`supabase/functions/api-key-reveal/index.ts:30-49`). Um 401 também vira a mesma mensagem genérica.
- Contra: a tela conseguiu listar `api_keys` sob RLS e mostra dados atuais, evidência de sessão funcional. O mesmo cliente Supabase injeta a sessão na invocação. Ainda pode ocorrer se a sessão expirar exatamente entre a listagem e o clique ou se houver problema de refresh.
- Como confirmar: status 401 e corpo `Token de autenticação inválido ou expirado`; repetir após logout/login.

### H3 — exceção interna por configuração/segredo da função

- A favor: URL/anon key/service role ausentes ou inválidos podem causar falha; o catch devolve 500 (`supabase/functions/api-key-reveal/index.ts:97-102`).
- Contra: `SUPABASE_URL` e chaves padrão costumam ser disponibilizadas automaticamente às Edge Functions; outras funções usam o mesmo padrão. Não há log fornecido mostrando exceção.
- Como confirmar: log `[API_KEY_REVEAL] Erro crítico` no Dashboard e resposta 500.

### H4 — migration/RPC do Vault ausente ou com permissão errada

- A favor: a versão atual depende de `get_bot_config_api_key`, criada em `supabase/migrations/20260831010200_bot_configs_api_key_vault.sql:34-79`.
- Contra: o código ignora o campo `error` da chamada RPC (`supabase/functions/api-key-reveal/index.ts:72-75`). Assim, RPC ausente/negada vira `vaultKey` nulo e o código retorna **200** com `reason: not_synced`, não o erro não-2xx da imagem. Portanto esta hipótese não explica diretamente o sintoma observado na versão local.
- Como confirmar: comparar a versão remota da função e o histórico de migrations; verificar a RPC sem ler o segredo.

### H5 — chave antiga ou Vault fora de sincronia

- Descartada para este sintoma na versão local: chave ausente/defasada retorna HTTP 200 (`index.ts:65-69` e `86-90`), que produziria o aviso “regenere a chave”, não `non-2xx`.

### H6 — RLS bloqueando a leitura da chave

- Descartada como causa direta: `api-key-reveal` usa cliente com `service_role` para `api_keys` (`index.ts:52-63`), portanto não depende da policy RLS do usuário. Além disso, a listagem já funciona na imagem.

## 5. Opções de correção

### Opção 1 — corrigir o rollout de `api-key-reveal` (recomendada; causa)

- O que mudar: confirmar/aplicar primeiro a migration `20260831010200_bot_configs_api_key_vault.sql`; depois implantar `api-key-reveal` e também alinhar `api-key-generate`/`api-key-revoke` à versão Vault. Atualizar `API_E_INTEGRACOES_LINK_OFERTA.md:148-154` e o pipeline/checklist para incluir `api-key-reveal`.
- Prós: corrige a provável causa; mantém o desenho de segurança com segredo no Vault; previne recorrência em novos ambientes.
- Contras: exige janela coordenada e acesso de deploy ao Supabase.
- Risco: médio se migration e funções forem publicadas fora de ordem; o próprio comentário da migration exige coordenação (`20260831010200...:19-25`).
- Esforço: baixo a médio.
- Validação: função presente e com versão atual; chamada autenticada retorna 200; chave ativa criada após sincronização é revelada e seu final coincide com `key_last4`; chave antiga retorna 200/`not_synced`.

### Opção 2 — melhorar observabilidade e tratamento do erro (complementar; sintoma)

- O que mudar: em `ApiKeyService.ts`, ao receber `FunctionsHttpError`, ler com segurança o corpo/status e mapear 401, 404 e 500 para mensagens úteis sem expor dados; na função, validar e registrar erros das queries/RPC com código/correlação, sem registrar tokens ou a chave.
- Prós: o usuário e a equipe deixam de receber uma mensagem opaca; acelera futuros diagnósticos.
- Contras: sozinho não faz o olho funcionar.
- Risco: baixo, desde que nenhum segredo/corpo sensível seja logado.
- Esforço: baixo.
- Validação: testes simulando 401/404/500 e conferindo mensagens sanitizadas.

### Opção 3 — remover a revelação permanente e manter exibição única na geração (alternativa de produto/segurança)

- O que mudar: retirar o olho e deixar a chave visível apenas no modal de criação; remover a necessidade de manter o token reversível no Vault para esse recurso.
- Prós: menor superfície de exposição de credenciais; comportamento já anunciado no próprio modal (`ApiIntegrationsTab.tsx:481-500`).
- Contras: pior experiência; usuários que perderem a chave precisam regenerá-la e atualizar integrações.
- Risco: médio operacional (integrações quebram se o usuário regenerar sem coordenação).
- Esforço: médio.
- Validação: geração exibe uma vez; depois só metadados aparecem; regeneração invalida a anterior.

**Recomendação:** Opção 1, acompanhada da Opção 2. A primeira corrige o provável descompasso de infraestrutura; a segunda transforma futuros 4xx/5xx em diagnóstico acionável. A Opção 3 só deve ser escolhida como decisão deliberada de segurança/produto.

## 6. Como reproduzir, validar e teste sugerido

### Reprodução

1. Entrar com usuário que possua uma chave ativa.
2. Abrir a aba de API/Integrações.
3. Abrir DevTools > Network e clicar no olho.
4. Inspecionar somente status e mensagem sanitizada da requisição `api-key-reveal` (não copiar JWT nem chave).
5. Correlacionar horário/request ID com o log da Edge Function.

### Validação da correção

- Caso sincronizado: HTTP 200, chave aparece e `SHA-256(chave)` corresponde a `api_keys.key_hash` no servidor.
- Caso antigo/não sincronizado: HTTP 200 com `reason: not_synced` e UI pede regeneração.
- Sessão expirada: UI mostra mensagem específica de autenticação e oferece novo login.
- Função inexistente: smoke test de deploy falha antes de publicar o frontend.

### Teste preventivo sugerido

- Teste de integração da Edge Function para: OPTIONS; sem Authorization (401); JWT inválido (401); sem chave ativa (200); Vault vazio (200 `not_synced`); hash divergente (200 `not_synced`); segredo válido (200 com chave).
- Teste do serviço/UI simulando `FunctionsHttpError` 401/404/500 e verificando mensagens sanitizadas.
- Smoke test de CI pós-deploy que confirme a existência de todas as funções referenciadas pelo frontend, incluindo `api-key-reveal`.

## 7. Outros pontos com o mesmo risco

- `api-key-generate` ignora erro ao revogar a chave ativa anterior (`supabase/functions/api-key-generate/index.ts:47-56`); uma falha pode prosseguir e tentar criar outra chave ativa.
- `api-key-reveal` ignora erros da consulta a `api_keys` e da RPC do Vault (`index.ts:58-63`, `72-75`), convertendo problemas de infraestrutura em `no_active_key`/`not_synced` enganoso.
- `api-key-revoke` ignora erros ao ler/limpar o Vault (`supabase/functions/api-key-revoke/index.ts:74-90`), podendo deixar segredo defasado sem sinalizar.
- O modal afirma que a chave “será exibida apenas uma vez” (`ApiIntegrationsTab.tsx:499-500`), mas a tela oferece revelação posterior. Há inconsistência de produto e expectativa de segurança.
- O checklist/documento de deploy não acompanha todas as funções que o frontend chama, criando risco equivalente em novos ambientes.
